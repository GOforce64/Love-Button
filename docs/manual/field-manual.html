Overview

The big picture

In plain words

The Love Button sends one of four fixed messages to the other phone: “I love you”, “Thinking of you”, “Miss you” or “Call me when you can”. Each has its own home-screen widget, pixel picture and sound, so she knows which one it is without looking. The sender’s widget shows the message travelling and turns gold once she’s seen it.

Phones can’t reach each other directly: they have no fixed address and are usually asleep. So a small server that both can always reach carries the message, and it asks Google’s push service, the only thing that can wake a sleeping Android phone, to deliver it.

Under the hood

  • Phones sit behind NAT: they can connect out to the internet but nothing can connect in. Doze also cuts idle apps off the network. The one line that stays open into an Android phone is Google Play Services’ connection to Google, and FCM is how a server sends down it.
  • Using FCM needs a Google service-account private key that can push to any phone in the Firebase project. Anyone can unpack an APK, so the key can’t go in the app; it lives only on the server.

Why it’s built this way

  • The push carries a number, never words. Her phone gets msg_id: 3 and looks up the text, picture and sound itself. The words never pass through Google.
  • No request names the recipient. The server works it out as 3 − sender’s number (people are 1 and 2), so there’s nothing to fake: even a stolen token can only message its own partner.

End to end

One tap, end to end

In plain words

You tap “Miss you”. Your phone gives the tap an id and tells the Worker “message 3”. The Worker checks it’s you, writes the message down and asks Google to wake her phone. Her phone plays the Miss-you sound and reports “delivered”, and your widget turns pink. When she looks at her phone it reports “seen”, and your widget turns gold. It normally takes a few seconds.

  1. 1Phone A
    Tap. SendAction shows the half-filled heart, then beginSend() makes a send_id (a UUID), saves it with the tap time, and queues two jobs: SendWorker (waits for internet) and TimeoutWorker (waits 20 seconds).
  2. 2Phone A
    Send. SendWorker notes which widget the send_id belongs to, then sends POST /v1/send with {"msg_id":3,"send_id":"…"} and the phone’s bearer token. No recipient.
  3. 3Worker
    Who is it? It hashes the token with SHA-256 and finds the phone’s row. That, and only that, decides the sender.
  4. 4Worker
    Check and save. Under 500 sends this hour, msg_id is 1–4, send_id is a UUID; otherwise an error status code (429 or 400). It saves the message with to = 3 − from and the server’s clock, sent_at.
  5. 5Worker
    Push. It asks FCM for a data-only, HIGH-priority push to each of her phones, then replies to Phone A with sent_at. Phone A’s tile turns crimson: sent.
  6. 6Phone B
    Buzz. Play Services wakes the app; PushService posts the notification on the “Miss you” channel, which plays its sound, then reports delivered. If she’s looking at her phone it also reports seen; if not, it waits for her next unlock.
  7. 7Worker
    Receipt. POST /v1/receipts: only the recipient may acknowledge (403 otherwise). It records the time and pushes the receipt to the sender at NORMAL priority.
  8. 8Phone A
    The tile climbs. Pink for delivered, gold for seen, but only within 20 seconds of the tap. Gold stays for 4 seconds, then the tile rests.

Why it’s built this way

  • The phone makes the id, not the server. The receipt can overtake the server’s reply. Because Phone A wrote down which tile the id belongs to before sending, it always knows which tile to light.

Server side

The server

In plain words

The Worker is about 960 lines of code that Cloudflare runs whenever a request arrives. It holds the Google key, decides who may send what to whom, and is the only place anything is stored outside the two phones.

Under the hood

  • No machine to run. Cloudflare runs the code on workerd, built on V8, in a lightweight isolate, in the data centre nearest the caller, only while a request lasts. It gets web-standard tools (fetch, WebCrypto), not Node.js. The free plan allows 100,000 requests a day and 10 milliseconds of CPU per request.
  • Routing. Hono sends each request to the function that handles it. Every reply is JSON, and every error has one shape: {"error": "rate_limited", "message": "…"}.
  • No passwords. wrangler.toml hands the code its database and cache as ready-made objects (bindings: env.DB, env.TOKEN_CACHE). Public settings (the Firebase project id, the two names) are plain vars. The three secrets (two enrolment codes and the service-account key) are uploaded with wrangler, stored encrypted, and can never be read back.

The database

D1 is SQLite run by Cloudflare. It has two tables:

TableColumns
devicesOne row per phone: id, person (1 or 2, enforced by a CHECK constraint, so a third person is impossible), auth_hash (SHA-256 of its token), fcm_token (its push address; empty for a send-only device), label, created_at, updated_at.
sendsOne row per message: id (the phone’s send_id), from_person, to_person, msg_id, sent_at, delivered_at, seen_at.

Times are epoch seconds. A cron job deletes messages older than 7 days every night at 03:17 UTC: the rows are only needed for receipts and the hourly limit, not as a history. KV holds two short-lived things: the Google access token (55 minutes) and a count of enrolment attempts per IP address (one hour).

The six endpoints

EndpointNeedsDoes
GET /healthnothingAnswers {"ok":true}.
POST /v1/enrolla codeTrades an enrolment code for a 256-bit bearer token, sent once; only its hash is kept. 5 tries an hour per IP address.
POST /v1/devicestokenSaves the phone’s new push address.
DELETE /v1/devicestokenDeletes the phone (the app has no button for this yet).
POST /v1/sendtokenSends a message (Chapter 2). Limit: 500 an hour per person.

Why it’s built this way

  • Identity only comes from the token. The requireDevice middleware hashes it and looks it up; nothing ever reads a sender from the request body.
  • Nothing can happen twice. A message is saved with INSERT OR IGNORE, so a repeated id is refused (409) instead of overwritten. A receipt uses COALESCE (“keep the time already recorded”), so repeating it changes nothing and the state never goes backwards.
  • No SQL injection. Values are passed separately from the SQL as placeholders (?), never pasted into it.

Server ↔ Google

Talking to Google

In plain words

To wake her phone, the Worker asks FCM to deliver a small message. Google only accepts that from the project’s owner, so the Worker signs a note with its private key, swaps it for a pass that lasts an hour, and shows the pass with every push.

IdentityWhat it isKept
google-services.jsonThe app’s identity: project id and an API key that only works for this app.Inside the APK. Not secret.
Service-account keyThe server’s identity: an RSA private key that can push to any phone in the project.Only as a Worker secret.
Registration tokenA phone’s push address, made by Play Services. It can change.In devices.fcm_token.

Under the hood

Getting the pass is OAuth 2.0’s signed-token flow:

  1. Write a JWT saying who is asking (the key’s email), for what (sending pushes) and until when (one hour).
  2. Sign it with the private key using RS256 through WebCrypto.
  3. Send it to oauth2.googleapis.com/token. Google checks the signature and returns an access token valid for one hour.
  4. Keep it in KV for 55 minutes, and send it with each push:
POST https://fcm.googleapis.com/v1/projects/lovieapp-b4068/messages:send
Authorization: Bearer ya29.…              ← the access token

{ "message": {
    "token": "<her phone's registration token>",
    "data": { "type": "msg", "send_id": "8b1f5a4e-…", "msg_id": "3",
              "from_name": "Hubby", "sent_at": "1788274056" },
    "android": { "priority": "HIGH" } } }

Why it’s built this way

  • The cache is required. An RSA signature uses nearly the whole 10-millisecond CPU allowance, so signing on every send would break the free plan. With the cache, about one request an hour pays for it.
  • Data-only. A notification message is drawn by Android itself and skips the app’s channels, and with them the four sounds. A data message is handed to the app’s code, which picks the channel.
  • HIGH for messages, NORMAL for receipts. HIGH wakes a phone even in Doze. Receipts aren’t urgent, and NORMAL saves battery.
  • Only UNREGISTERED deletes a phone. Other errors can come from a bad request that fails for every phone at once. Deleting them all would lock her out until she enrolled again.

When Play Services gives a phone a new address, the app sends it to /v1/devices through a background job. FCM holds messages for a phone that’s switched off (by default for up to four weeks), but a force-stopped app never receives them.

Phone side

The app

In plain words

The app is the screen you open plus the four widgets. Behind them are background jobs that do the sending, and a few small files that remember what’s going on.

Under the hood

  • Start-up. Android starts the app’s process for anything: opening it, a push, a widget tap. Each time, LoveButtonApp creates the notification channels and starts listening for unlocks. The screen shows Enrol until the phone is enrolled, then Home.
  • Enrolling. Once per phone: the app gets its push address from Play Services, sends it with the enrolment code to /v1/enroll, and saves the token, person number and partner’s name.
  • Storage. Five small DataStore files in app-private storage, kept out of cloud backups:
FileHolds
love_buttonThe token, which person this phone is, the partner’s name.
current_sendThe one latest message, shown on the app screen.
pending_sendsWhich widget each recent message came from (about 20 seconds).
unseen_sendsMessages that arrived while nobody was looking.
delivery_setupWhether you confirmed the Xiaomi settings.
Background jobWaits forDoes
SendWorkerinternetSends the message and updates the widget.
TimeoutWorker20 seconds onlyTurns a widget grey if it’s still waiting.
ReceiptWorkerinternetReports delivered or seen.
RegisterTokenWorkerinternetSends a new push address.

Why it’s built this way

  • Everything goes through WorkManager. Xiaomi kills app processes routinely (process death). A request started straight from a tap would vanish; a WorkManager job is saved to disk and finishes later.
  • One attempt per message. A failed send asks for a retry, but WorkManager’s first retry comes after 30 seconds, when the 20-second window has closed, so it’s dropped. A tap only counts while the sender is still waiting for it.

Phone B

Receiving a message

In plain words

When the push reaches her phone, it plays that message’s sound with a notification and tells the server “delivered”. As soon as she’s actually looking at her phone, it tells the server “seen”.

IdMessageChannelSoundWidget
1I love youmsg_1love.ogg
2Thinking of youmsg_2thinking.ogg
3Miss youmsg_3miss.ogg
4Call me when you canmsg_4call.ogg

Under the hood

  • Channels. Since Android 8, a notification’s channel decides its sound. The app has four, created at every start-up (creating an existing one does nothing), each with high importance and its sound: android.resource://com.lovebutton.app/raw/miss.
  • The notification. Title: the sender’s name. Text: the message. A white heart icon, tinted crimson; a new id each time so several messages stack. On Android 13 and newer it needs the notification permission.
  • Delivered is reported only after the notification has been posted.
  • Seen means she looked at her phone, not that she tapped the notification: the screen is on and unlocked (not on the lock screen). If so it’s reported at once. If not, the message waits in unseen_sends and UnlockReceiver reports it the next time she unlocks.
The one thing that can’t be undone

Android never lets an app change a channel’s sound after the channel is created; the only way is to delete it, which resets her settings. So the four sounds were final before the channels first existed.

Why it’s built this way

  • The sound is addressed by its file name, because resource numbers change between builds while a channel keeps its sound address forever.
  • The unlock listener is registered in code: since Android 8, the unlock broadcast isn’t delivered to listeners declared in the manifest. If Android kills the app before she unlocks, no “seen” is sent: silence, never a false “seen”.

The ladder and the bubble

In plain words

The sender’s widget climbs a ladder: outline, half-filled, crimson, pink, gold. If nothing comes back within 20 seconds it turns grey instead. The app screen shows the same states, animated, and both phones agree on one “latest message”.

StateMeansShown for
IDLEResting.—
SENDINGTapped; no reply yet.Until the request ends
SENTThe server has it.Up to 20 seconds
FAILEDFailed, or no reply in 20 seconds.3 seconds
DELIVEREDHer phone showed it.Up to 20 seconds
SEENShe looked at her phone.4 seconds

Under the hood

  • Only forward. Each state has a rank (IDLE 0, SENDING 1, SENT 2, FAILED 3, DELIVERED 4, SEEN 5), and a receipt is written only if it moves the rank up. Her two receipts can arrive in either order, and a late “delivered” must not turn gold back to pink.
  • The 20-second window (PENDING_WINDOW_MS). The app screen shows anything still waiting after 20 seconds as grey. TimeoutWorker greys the widget; it has no network condition, so it also fires with no signal. SendWorker drops a request that only found a connection after the window. Late receipts are still recorded, but never light the widget.
  • One writer at a time. Every change goes through WidgetStateWriter, which checks and writes in one step, and a timer only resets the picture it put there. That prevents a race condition.
  • The app screen remembers. Where the widget goes back to rest, the app keeps showing how the latest message ended. It draws the icon pixel by pixel so it can animate it (rising fill, a ripple, gold running round the edge).

The shared bubble

The app screen’s card shows the latest message between you, whoever sent it, and both phones must agree on which that is. An arriving message takes the card if its server time (sent_at) is later. In a tie within the same second, the higher send_id wins. Your own message still in flight has no server time yet, so it gives way, then takes the card back when its reply arrives if what replaced it is older.

Why it’s built this way

  • Phone clocks differ, so only the server’s clock is compared. It counts whole seconds, so ties are common, and the id tie-break gives the same answer on both phones (a total order).

Phone side

Widgets and pixel art

In plain words

A widget isn’t running anything: it’s a picture your home screen draws for the app. So each state is a finished picture, and every picture is drawn by a script from a grid of letters in the code.

Under the hood

  • Widgets. The home screen (the launcher) is a separate app. A widget reaches it as RemoteViews sent across IPC: a few standard building blocks, with no custom drawing or animation. That’s why the ladder swaps whole pictures.
  • Four widgets, one class. The widget list shows four entries (each 2×2 cells), all using MessageWidget with a different message id. A tap writes SENDING and calls beginSend(). After a reboot, BootReceiver redraws them.
  • Pixel art. scripts/pixel_icons.py holds each icon as a grid of letters (X solid, . empty) and turns it into the 20 widget pictures (4 icons × 5 states).

Everywhere

Security

In plain words

The code is public, so safety can’t depend on it being secret. It depends on three rules the server always checks, tokens that are useless if copied, and three secrets that live only on the server.

Under the hood

The three invariants, each with a test:

  1. The sender is the phone that proved who it is. Nothing reads a sender from the request.
  2. The recipient is worked out on the server, as 3 − from_person. No request can name one.
  3. Only the recipient may acknowledge a message. Otherwise a sender, who knows every send_id, could fake “seen”.
  • Tokens are 32 random bytes (256 bits), sent once and stored only as a SHA-256 hash, so a stolen copy of the database holds no working keys.
  • Enrolment codes are 48 hex characters, one per person, limited to 5 tries an hour, and checked with a constant-time comparison, so timing reveals nothing (a timing attack). Changing a code stops new enrolments but doesn’t cut off an enrolled phone; for that you delete its row.
  • On the phone, the token sits in app-private storage and is never logged; the release build can’t be inspected over USB. A pre-commit hook refuses any commit containing a private key or a secrets file.

The three real secrets (the service-account key and the two enrolment codes) live only as Worker secrets and in a password manager; the release keystore that signs the app is kept outside the repo. Not covered: someone holding her unlocked phone, and end-to-end encryption. The pushes pass through Google, but they only ever say “message 3”.

Reliability and limits

In plain words

Xiaomi’s phone software, MIUI, kills background apps far more than normal Android. The app can’t change those settings itself, so its Delivery setup screen shows where each one is.

SettingDefaultWhat it breaks
Battery optimisation (Android)OnBackground work is delayed. The app asks to be exempt.
Autostart (Xiaomi)Off for sideloaded appsA push can’t start the app; widgets aren’t redrawn after a reboot.
Battery saver (Xiaomi)“Restricted”Background work is suspended. Set “No restrictions”.
Lock in recents (Xiaomi)UnlockedThe app is cleared when memory runs low.

The Xiaomi settings can’t be read by an app, so you confirm them by hand, and the Home screen shows “Finish delivery setup” until you do.

Limits

  • Force stop: nothing arrives until the app is opened again, and missed messages aren’t replayed.
  • China ROM: no Play Services, so no FCM. Both phones must run Xiaomi’s Global or European (EEA) software.
  • No signal: the widget greys at 20 seconds and the message is dropped, not sent late.
  • Her phone off: she gets it when it’s back on; your widget will already be grey.
  • No sign-out button: a retired phone is removed on the server.
